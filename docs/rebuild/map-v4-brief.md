# 地图/建筑系统 v4 重建 Brief（外部评审用）

> 分支：`rebuild/maps-v4`（仅新增本文档，未删代码、未合并 main）
> 基于：main `154be4e`（v1.15.0）
> 目的：把当前地图模块的真实问题、根因、可选方案讲清楚，供 ChatGPT 等外部评审参谋；
> 结论未定前不对 main 做破坏性删除。

---

## 1. 结论先行

当前 `js/world.js`（1589 行）+ `js/maps/*.js`（3 张图）+ `TownGen` + 建筑导入器这套架构，
在“新模型替换”后暴露出结构性问题，继续打补丁收益很低：

**建议保留渲染/单位/武器/AI/网络，重建“地图 + 碰撞 + 导航”这一层（v4）。
是否连地图数据一起全部删掉重来，需要外部评审给意见（见 §8）。**

用户实测反馈（全部成立）：

1. 所有楼层都太矮，建筑整体“小了一圈”。
2. 仍能看到旧模型。
3. 战壕、沙包、部分建筑可以穿过去。
4. 空气墙没有解决。

这不是单点 bug，而是“尺寸契约、碰撞来源、导航模型、地图构建”四件事没有统一。

## 3. 缺陷与根因（按用户反馈逐条）

### 3.1 尺寸/楼层整体小一圈

**根因：新模型按“包内原生尺寸”接入，没有按游戏原有玩法尺度放大。**  
导入器只做了归一化和统一缩放（map scale=1），没有全局资产倍率。

| 类型 | 旧游戏尺寸 (w×d×h) | 新模型原生尺寸 | 比例 |
|---|---|---|---:|
| house | 10.6×8.6×4.3 | 10.8×8.59×6.32 | 占地≈1，层高变高 |
| apartment | 16×12×19.1（5 层≈4m/层） | 12.4×11.02×7.58（2 层） | 0.69 / 0.40 |
| warehouse | 22×14×9.7 | 14.34×10.7×6.14 | 0.65 / 0.63 |
| guardhouse | 5×5×4.5 | 4.18×3.98×3.35 | 0.84 / 0.74 |
| bunker | 18×14×8 | 12.4×7.58×4.49 | 0.69 / 0.56 |
| base（实际落地） | ≈89×74×26 | 86.55×66.68×11.8 | 高度 0.45 |
| cover | 14.5×6.3×2.75 | 14.15×5.74×2.1 | 0.91 / 0.76 |

楼层高度实测（平台大面）：

- apartment：0.20 / 3.06 / 6.08m（旧版 4 / 8 / 12m）
- house：0.17 / 2.99 / 5.96m
- base：0.30 / 4.90 / 8.71 / 9.15 / 11.8m
- workshop：0.20 / 6.21m

玩家眼高 1.7m，3m 层高本身可用，但与旧玩法“4m 层高、19m 公寓、26m 基地”的尺度相比明显缩水；
地图旧布局、掩体间距、镜头/武器比例都是按旧尺度设计的。

**待决策**：新资产统一 ×1.3~1.5 放大后重排地图，还是按新尺度重做地图与玩家空间感？  
如果只放大模型、不重排地图，旧地图的间距/压平垫/碰撞会再次错位。

### 3.2 仍看到旧模型

不是缓存问题（已修 `force-cache`），是**新包只覆盖了部分类型**：

- 已替换：house / apartment / warehouse / guardhouse / bunker / base / cover
- 新增：house_small / farmhouse / workshop / pumpstation / estate
- **仍保留旧模型**：container、watchtower、stairs、bridge、wall、ruins、hangar、pillbox、
  crane、tankH、tankV、mast、tower、megatower、stadium、refinery、complex

用户看到这些会认为“旧建筑没删”。如果要求“全部换新”，需要先补齐这些类型的模型，
或者在地图 v4 中把对应玩法元素改成新资产/程序化资产。

### 3.3 战壕/沙包/部分建筑可以穿过

根因不止一个：

1. **战壕**：当前是 `terrain`/`ruins`/`cover` 的视觉数据，部分没有碰撞体，或只有地面压平。
2. **沙包**：`cover` 是“混凝土墙 + 沙袋 + 护栏”组合模型，碰撞来自构件 AABB/栅格；
   视觉与碰撞不是同一份三角数据，缝隙/低矮处容易不一致。
3. **聚合墙体（重大 bug）**：导入器 `scripts/import_buildings.cjs` 的 `voxelRects()` 只沿三角
   **边**采样 0.4m 格子并合并，**没有填充三角形内部**。base 的大面墙板/围墙只有边缘格子，
   墙体中间没有碰撞 → 玩家可以直接穿过墙面。v31 测试只验了边界/门洞/nav，没有做
   “每面视觉墙都必须挡人”的射线一致性测试，所以没抓到。
4. 旧类型仍使用手写 CONFIGS/AABB，和新视觉本来就不完全一致。

### 3.4 空气墙

- 旧类型手写 CONFIGS 的碰撞盒与视觉几何不是同源；模型换过一次后，旧 CONFIGS 只是回退值。
- 聚合大件曾用整体 AABB（把内部填实），后来改成栅格化，但栅格化本身有 §3.3 的漏洞；
  两侧误差会同时表现为“能穿”和“空气墙”。
- 2D 导航网格（2m）与 3D 碰撞/平台是两套数据；门洞要额外打洞，楼梯/楼层要额外平台，
  任何一处漏配都会出现“视觉能走但碰撞挡/视觉该挡但能穿”。

### 3.5 架构层面的问题

- `world.js` 同时负责渲染、碰撞、导航、地图生成、小地图、据点、出生、机制、合批；
  任何一个环节改尺寸都要全局联动。
- 地图数据（`js/maps/*.js`）手写坐标 + `TownGen` 运行时生成 + 导入器生成元数据，
  三套来源，没有单一的可验证场景描述。
- 缺少硬性门禁：
  - 视觉包围盒 vs 尺寸契约
  - 视觉墙面 vs 碰撞面的射线一致性（防穿墙/空气墙）
  - 地面/楼层高度与层高契约
  - 门/楼梯/平台 nav 连通
  - 出生点/据点/掩体可达性与性能预算

当前测试（`_qa_v31_models.js`）只覆盖了元数据/边界/门洞 nav，不覆盖上述最关键的两项：
**视觉-碰撞一致性、层高契约**。

## 4. 可选的 v4 方案

### 方案 A（推荐）：保留渲染/单位/AI/网络，重建“地图 + 碰撞 + 导航”

- 资产契约：
  - 每个建筑 GLB 必须包含：渲染 mesh + **碰撞代理 mesh**（三角/凸包，与视觉同源或显式代理）
    + 元数据（dims、楼层标高、门/窗/楼梯锚点、nav 入口）。
  - 全局资产倍率（如 ×1.4）只在一个 manifest 声明，地图/碰撞/平台统一乘。
- 碰撞：
  - 用碰撞代理三角 mesh + BVH 做射线/移动检测；不再从构件名/AABB/栅格猜。
  - 楼板/楼梯用显式 walkable surface（三角或平台带法线），不做 2D 猜测。
- 导航：
  - 1m 栅格 + 门/楼梯 off-mesh link，或 navmesh + portal；高度感知。
  - 不再依赖 2m 栅格打洞。
- 地图：
  - 单一声明式 map spec：对象引用资产、transform、scale、碰撞代理、nav 入口、区域语义。
  - 程序化 TownGen 只产出 spec，不直接写 colliders；生成后跑完整校验。
- 验证门禁（必须自动化）：
  1. 视觉 bbox = 契约尺寸（±1cm）。
  2. 每面外/内墙：视觉射线命中点与碰撞射线命中点一致（防穿墙/空气墙）。
  3. 层高/净高 ≥ 契约（玩家 1.8m，门 ≥2.2m）。
  4. 门洞两侧 nav 连通；楼层/楼梯可走。
  5. 出生点→3 据点 A* 连通；无碰撞体与出生点重叠。
  6. 性能预算（draw call/tris/碰撞查询/AI LOS）。

### 方案 B：地图模块全部删除，从空白场景重建

- 删除 `js/world.js` 的地图部分、`js/maps/*`、TownGen、旧 CONFIGS/CONFIGS 回退。
- 保留：渲染器、单位/武器/AI/网络/UI/音效。
- 成本最高，但能彻底摆脱旧尺度/旧数据；需要重新做 3 张图。
- 适合“旧地图数据本身也不可信”的情况；用户目前倾向这个方向。

### 方案 C：只重建碰撞/导航层，保留现有地图布局

- 最快止血：不改地图/尺寸，先把碰撞换成同源代理、nav 换成高度感知。
- 但解决不了“尺寸小一圈/旧模型/楼层矮”，只能解决穿墙/空气墙。
- 不建议作为最终方案。

## 5. 建议的分支/迁移策略

1. 本分支 `rebuild/maps-v4` 只放本 Brief + 可复现证据，main 保持稳定。
2. 评审确定方案后，再开：
   - `rebuild/maps-v4-assets`：资产倍率/碰撞代理/元数据契约；
   - `rebuild/maps-v4-runtime`：新碰撞 + nav + map spec；
   - `rebuild/maps-v4-content`：三张图重排。
3. 旧地图数据在 v4 runtime 跑通并通过门禁前不删除（保留回退）。
4. 最终切换：main 只保留一套 map runtime，旧 world/maps 移入 `legacy/` 或删除。

## 6. 需要外部评审回答的问题

1. **尺度**：新资产统一放大到旧玩法尺度（×1.3~1.5）还是按新尺度重做地图/出生/据点/镜头？
   玩家眼高 1.7m 是否应保持不变（建议保持）？
2. **碰撞表示**：三角 mesh + BVH、凸包分解、还是“视觉同源代理”混合？
   性能预算（当前 3000+ colliders / 3700 platforms / 20 AI）下哪个可行？
3. **导航**：1m 栅格 + portal，还是 navmesh + off-mesh link？门 1.4m、楼层 3~4m 的场景怎么选？
4. **地图描述**：声明式 spec + 离线烘焙，还是运行时程序化生成？
   手写地标/程序化街区如何共存且可验证？
5. **删除范围**：只删 `world.js` 地图部分 + `js/maps/*`，还是连 `TownGen`/旧 CONFIGS/旧 GLB 一起删？
   哪些渲染/合批/A* 代码值得保留？
6. **验收标准**：视觉-碰撞射线一致性、层高、门/楼梯 nav、A* 连通、性能，优先级怎么排？
7. **迁移风险**：三张图重做的工作量/顺序；先做一张基准图（suburb）还是三张并行？
